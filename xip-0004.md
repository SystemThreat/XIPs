## Abstract

Nodes talk to each other over BIP324, the encrypted "v2" transport xCoin
inherited from Bitcoin Core. Its keys come from one elliptic-curve
Diffie-Hellman exchange, which a large quantum computer could break. Anyone
who records node traffic today could then read it later. HX1 adds an
ML-KEM-768 key exchange (FIPS 203) inside BIP324's own version packets, then
moves every later packet to new keys that depend on both the ECDH secret and
the ML-KEM secret. To read HX1 traffic later, an attacker must break both.
Old BIP324 nodes ignore the new packet contents, so old and new nodes still
connect; they just stay classical. HX1 changes no block or transaction rule
and cannot fork the chain. It shipped in the mainnet genesis release
(2026-09-26, XIP-6) and is on by default.

## Motivation

xCoin's coins are already protected against quantum computers: spending needs
ML-DSA-65 or SLH-DSA signatures. The node-to-node link is not. BIP324 hides
which node first relayed a transaction, what nodes gossip about each other,
and what they ask for, but only from someone who cannot break secp256k1. A
recording made now can be decrypted by whoever holds a large enough quantum
computer later ("record now, decrypt later"). For a network whose whole
identity is post-quantum, relay privacy is the remaining classical piece.

BIP324 itself names "post-quantum cryptography upgrades to the handshake" as a
future version feature, and reserves the version packet for such extensions:
receivers ignore its contents today (src/net.h:464-467, src/net.cpp:1249-1255;
all line references in this XIP are to the public tree at tag
v31.99.0-pre1, commit c07d047). That hook is what makes HX1 a Policy change
rather than a new protocol.

The founder postponed mainnet genesis (originally September 30, 2026) so that
HX1 would be in the genesis release; genesis was then mined on 2026-09-26 once
HX1 was merged (XIP-6). Every mainnet node since genesis runs it, and no v2
link between two mainnet nodes on default settings runs classical-only.

## Specification

The key words MUST, MUST NOT, SHOULD and MAY are used in their usual sense.

### Terms

- **Initiator / responder.** The node that opened the TCP connection /
  the node that accepted it. BIP324 uses the same words.
- **Stage 1.** BIP324 exactly as implemented today: ElligatorSwift keys,
  garbage, garbage terminators, the ECDH secret and the six HKDF outputs
  (src/bip324.cpp:34-71), packet encryption (src/bip324.cpp:73-109).
- **Stage 2.** The four packet keys and session id derived by this XIP.
- **Version packet.** The first packet in a direction after the garbage
  terminator whose ignore bit is clear. Decoy packets (ignore bit set) may
  come before it (BIP324; src/net.h:515-523).
- **VP_R / VP_I.** The responder's / initiator's version packet.
- **ek, dk, ct, K.** ML-KEM-768 encapsulation key (1184 bytes),
  decapsulation key (2400 bytes), ciphertext (1088 bytes) and shared secret
  (32 bytes), as in FIPS 203 section 8, Table 3.
- **ell_I, ell_R.** The 64-byte ElligatorSwift public keys each side sends
  first. **ecdh_secret** is the 32-byte BIP324 ECDH secret, which already
  hashes both of them (src/key.cpp:328-345).
- **MessageStart.** The 4-byte network magic: mainnet `58 50 41 03`,
  testnet A `58 54 41 02`, regtest `4e 45 58 03`
  (src/kernel/chainparams.cpp:272-275, 448-451, 603-606).

### Constants

| Name | Value |
|---|---|
| HX1 tag | 8 ASCII bytes `xcoin-pq` = `78 63 6f 69 6e 2d 70 71` |
| HX1 version byte | `0x01` |
| Record kind OFFER | `0x01`; body is ek, 1184 bytes |
| Record kind ACCEPT | `0x02`; body is ct, 1088 bytes |
| Record header | 12 bytes: tag (8) ‖ version (1) ‖ kind (1) ‖ body length (2, little-endian) |
| OFFER record | 1196 bytes; VP_R on the wire 1216 bytes |
| ACCEPT record | 1100 bytes; VP_I on the wire 1120 bytes |
| Stage-2 salt | ASCII `xcoin_v2_hybrid_mlkem768` ‖ MessageStart (28 bytes) |
| Stage-2 labels | `xcoin_hx1_initiator_L`, `xcoin_hx1_initiator_P`, `xcoin_hx1_responder_L`, `xcoin_hx1_responder_P`, `xcoin_hx1_session_id` |
| Stage-2 input key material | K ‖ ecdh_secret ‖ ct ‖ ell_I ‖ ek ‖ ell_R (2464 bytes) |
| Rekey interval | 224 packets, unchanged (src/bip324.h:24) |
| First stage-2 packet | at most 4095 bytes of contents, in each direction |
| Confirmation packet | the responder's first stage-2 packet: a decoy with empty contents, 20 bytes on the wire |
| Option | `-v2hybrid=<0\|1\|2>`, default `1` on every network |

The on-wire sizes follow from BIP324's 20-byte expansion per packet: 3 length
bytes, 1 header byte, 16 tag bytes (src/bip324.h:25-27).

### Modes

`-v2hybrid` is read once at startup and fixed for each connection when its
transport is created (src/net.cpp:3967-3974).

- **0, off.** The v2 transport behaves exactly as v31.99.0-pre1, byte for
  byte and state for state: it sends an empty version packet as soon as it has
  the peer's key, becomes ready at that moment (src/net.cpp:1143-1173), wipes
  the ECDH secret inside the stage-1 derivation (src/bip324.cpp:66-70), and
  ignores version packet contents (src/net.cpp:1249-1255). No ML-KEM code
  runs. This is the kill switch; see "Kill switch" below.
- **1, prefer (default).** Offers HX1 as responder and accepts an offer as
  initiator. With a peer that does not take part, the connection stays
  classical BIP324. Plaintext v1 behaviour is unchanged. An outbound connection
  whose HX1 handshake fails is retried once as classical v2 (see "Failure
  handling").
- **2, require.** HX1 or nothing:
  - A v2 peer that does not complete HX1 is disconnected.
  - Inbound plaintext v1 is refused: when the first 16 bytes match the v1
    prefix (src/net.cpp:1101-1114), the node disconnects instead of falling
    back.
  - Outbound connections always try v2, even to addresses whose advertised
    services lack NODE_P2P_V2 (today src/net.cpp:2895 and 3257 require the
    peer's bit). Seed addresses, which enter addrman without that bit
    (src/protocol.h:354), are therefore tried as v2 too.
  - The v1 reconnect never happens (`ShouldReconnectV1` returns false; today
    src/net.cpp:1555-1570), and there is no classical retry.
  - `addnode` and `addconnection` with `v2transport=false` fail with an RPC
    error (src/rpc/net.cpp:345-349, 417-424).
  - `-v2hybrid=2` together with `-v2transport=0` is a startup error.

With `-v2transport=0` (src/init.cpp:1006-1009) no v2 transport exists, so
modes 0 and 1 have no effect. Any `-v2hybrid` value other than 0, 1 or 2 is a
startup error.

### Version packet contents

A version packet's contents are either empty or one HX1 record, byte for
byte:

```
offset  size  field
0       8     tag      78 63 6f 69 6e 2d 70 71   ("xcoin-pq")
8       1     version  01
9       1     kind     01 = OFFER, 02 = ACCEPT
10      2     length   body length, little-endian: a0 04 (1184) or 40 04 (1088)
12      len   body     OFFER: ek (1184 bytes)   ACCEPT: ct (1088 bytes)
```

Senders in modes 1 and 2 put exactly one record and nothing after it: the
responder sends an OFFER, the initiator an ACCEPT. A mode-0 sender sends empty
contents, as today.

A receiver in mode 1 or 2 classifies the contents it got as follows. The rows
do not overlap: they are read from the front of the contents, and exactly one
fits. A receiver in mode 0 ignores the contents, as today.

| Contents | Classification |
|---|---|
| empty, fewer than 9 bytes, or the first 8 bytes are not the tag | **none** (the peer is classical, or sends an extension this node does not know; ignored as BIP324 requires) |
| the tag, then a version byte other than `01` | **none** (a later HX version this node does not speak) |
| the tag and version `01`, then anything but the expected record: the 12-byte header ends early, the kind is not the one expected in this direction, the length is not 1184 (OFFER) / 1088 (ACCEPT), or fewer body bytes follow than the length says | **malformed** |
| the tag, version `01`, the expected kind and length, and the whole body | **HX1**; the body is ek or ct |

The initiator expects an OFFER in VP_R; the responder expects an ACCEPT in
VP_I.

Only the first record is read. Bytes after its body are ignored; they are
reserved so that a later version can offer a second record. Such a version
MUST put its HX1 (version `01`) record first: an HX1 node looks only at the
first record, so a record of another version in front of it would make every
HX1 node treat the peer as classical.

### Message order

Stage 1 up to the version packets is unchanged BIP324 (src/net.cpp:989-1016,
1082-1205). What HX1 changes is when each version packet is sent and what
happens after it.

```
Initiator (outbound)                                Responder (inbound)

ell_I || garbage_I  -------------------------------->
                    <--------------------------------  ell_R || garbage_R
                                                       [has ell_I: stage-1 keys,
                                                        ML-KEM KeyGen -> ek, dk]
                    <--------------------------------  gt_R || VP_R{OFFER ek}   (stage 1)
[has ell_R: stage-1 keys]
gt_I                -------------------------------->
[has VP_R: check ek, Encaps -> ct, K]
VP_I{ACCEPT ct}     -------------------------------->  (stage 1)
[switch both directions to stage 2; ready]
VERSION             ================================>  (stage 2)
                                                       [has VP_I: Decaps -> K,
                                                        switch both directions
                                                        to stage 2; ready]
                    <================================  confirmation packet   (stage 2)
                                                       [VERSION authenticates:
                                                        hybrid confirmed]
[confirmation packet authenticates:
 hybrid confirmed]
                    <================================  VERSION, VERACK, ...  (stage 2)
```

In practice VP_R usually leaves in the same flight as ell_R: the initiator
sends its whole key at once, so the responder normally has it when it answers
(src/net.cpp:1094-1100 and 1143-1171 run in the same receive loop,
src/net.cpp:1338-1410). So the initiator's VERSION message leaves about when
it does today, and HX1 adds no round trip. Nothing waits for the confirmation
packet: the initiator has already sent VERSION, and uses the packet only to
confirm the keys.

#### Initiator, modes 1 and 2

1. On connect, send ell_I ‖ garbage_I. Unchanged (src/net.cpp:1011-1015).
2. On receiving the 64-byte ell_R, derive the stage-1 keys as today, but keep
   ecdh_secret (see "Secrets"). Append gt_I to the send buffer. Do **not**
   append VP_I, and do **not** become ready. (Today both happen here,
   src/net.cpp:1156-1171.) Sending gt_I now or together with VP_I puts the
   same bytes on the wire; the reference implementation sends it now.
3. Receive garbage_R and gt_R, then stage-1 packets, as today. The first
   packet authenticates garbage_R as associated data; decoys are skipped
   (src/net.cpp:1180-1264). The first non-decoy packet is VP_R.
4. Classify VP_R:
   - **none**: mode 1 appends an empty VP_I (stage-1 keys, garbage_I as
     associated data unless a decoy already carried it) and becomes ready; the
     session is classical and uses stage-1 keys from here on. Mode 2
     disconnects.
   - **malformed**: disconnect.
   - **HX1**: run the FIPS 203 section 7.2 encapsulation key check on the body
     (the length check is already done; the modulus check is
     `ByteEncode12(ByteDecode12(ek[0:1152])) == ek[0:1152]`, FIPS 203
     equation 7.1; ByteDecode12 reduces each 12-bit value modulo 3329, so any
     value of 3329 or more fails). If it fails, disconnect. Otherwise draw 32
     random bytes m from the node's strong RNG and compute
     (K, ct) = ML-KEM.Encaps_internal(ek, m) (FIPS 203 Algorithm 17).
     Append VP_I carrying the ACCEPT record, encrypted with the stage-1
     initiator keys (garbage_I as associated data unless a decoy already
     carried it). Then derive the stage-2 keys, replace **both** directions'
     ciphers with stage-2 ciphers, wipe the secrets, and become ready.
5. In the hybrid case, the next packet received MUST decrypt under the
   stage-2 responder keys. It is the responder's confirmation packet, which
   arrives about one round trip after VP_I. The first stage-2 packet that
   authenticates is **key confirmation**. Until then the first-packet limit
   applies (see "First stage-2 packet and key confirmation").

The initiator MAY send decoys before VP_I (stage-1 keys) and after it
(stage-2 keys). Its first stage-2 packet, decoy or VERSION, has at most 4095
bytes of contents. It MUST NOT send any application message before step 4 has
finished. Because application messages only go out in the ready state
(src/net.cpp:1492), the queued outbound VERSION
(src/net_processing.cpp:5811-5815)
waits until then, so no application message is ever sent under stage-1 keys
in a hybrid session.

#### Responder, modes 1 and 2

1. Detect v1 or v2 from the first 16 bytes, as today
   (src/net.cpp:1082-1118). In mode 2 a full v1 prefix match disconnects.
2. On v2, send ell_R ‖ garbage_R. Unchanged.
3. On receiving the 64-byte ell_I, derive the stage-1 keys as today and keep
   ecdh_secret. Draw d and z, 32 bytes each, from the node's strong RNG as two
   separate calls (see "Secrets": one 64-byte call would abort the node) and
   compute (ek, dk) = ML-KEM.KeyGen_internal(d, z) (FIPS 203 Algorithm 16).
   Append gt_R and VP_R carrying the OFFER record, encrypted with the stage-1
   responder keys (garbage_R as associated data unless a decoy already carried
   it). Do **not** become ready. (Today the responder becomes ready here,
   src/net.cpp:1156-1157.)
4. After VP_R the responder MUST NOT send anything, not even a decoy, until it
   has processed VP_I. Until then it cannot know which keys the initiator
   expects next.
5. Receive garbage_I, gt_I and stage-1 packets as today. The first non-decoy
   packet is VP_I. Classify it:
   - **none**: mode 1 wipes ek, dk and ecdh_secret, becomes ready, and stays
     classical on stage-1 keys. Mode 2 disconnects.
   - **malformed**: disconnect.
   - **HX1**: compute K = ML-KEM.Decaps_internal(dk, ct) (FIPS 203
     Algorithm 18). The ciphertext length check of FIPS 203 section 7.3 is
     already done by the record check; the decapsulation-key checks may be
     skipped because dk is this node's own fresh key. Derive the stage-2 keys,
     replace both directions' ciphers with stage-2 ciphers, wipe the secrets,
     append the **confirmation packet** (a decoy with empty contents, the
     first packet under the stage-2 responder keys), and become ready. The
     confirmation packet goes out at once, before the node's message
     processing has seen anything from this peer.
6. In the hybrid case, the next packet received MUST decrypt under the
   stage-2 initiator keys; it is normally the initiator's VERSION. The first
   one that does is key confirmation. Until then the first-packet limit
   applies.

Decapsulation never reports a bad ciphertext: ML-KEM's implicit rejection
returns an unrelated K (FIPS 203 Algorithm 18). A bad ct therefore shows up
as a stage-2 failure on the first stage-2 packet in each direction: under the
wrong key its length decrypts to a random value, which the first-packet limit
rejects about 4095 times in 4096. Implementations MUST NOT branch, log or time
differently on implicit rejection.

#### The switch point, per direction

Each side switches both directions at one moment: the initiator right after it
has encrypted VP_I, the responder right after it has decrypted VP_I. This
gives a fixed boundary on the wire:

- **Initiator to responder:** decoys before VP_I and VP_I itself use
  stage-1 keys. Every later packet uses stage 2.
- **Responder to initiator:** decoys before VP_R and VP_R itself use stage-1
  keys. The responder sends nothing more until it has VP_I; every later
  packet uses stage 2, starting with the confirmation packet.

In a classical session there is no switch and no confirmation packet: both
directions keep their stage-1 ciphers and counters, exactly as in BIP324.

#### First stage-2 packet and key confirmation

Each side's first packet under stage-2 keys has at most 4095 bytes of
contents. For the responder that is the confirmation packet (empty contents).
For the initiator it is its VERSION message, a few hundred bytes at most, or a
decoy it chooses to send first.

Until key confirmation, a receiver that decrypts a stage-2 length above 4095
MUST treat it as a stage-2 failure at once: disconnect, count
`stage2_failed`, and, for an initiator in prefer mode, retry classically. It
MUST NOT wait for that packet's bytes. After key confirmation the usual size
limit applies.

The limit is needed because the usual one never fires on a wrong key. When the
two sides' stage-2 keys differ (implicit rejection of a bad ct, a stripped or
altered record, any HX1 bug), the 3-byte length decrypts to a random value of
up to 16,777,215. xCoin's packet size limit is MAX_CONTENTS_LEN = 1 + 12 +
min(MAX_SIZE, MAX_PROTOCOL_MESSAGE_LENGTH) = 33,554,445 (src/net.cpp:1216-1218;
src/serialize.h:34; src/net.h:71), more than any 3-byte length, so the check
at src/net.cpp:1223-1226 cannot reject it. Without the first-packet limit the
receiver waits for bytes that never come until the handshake timeout, 60 s by
default (src/net.h:93). With it, each side catches a wrong key on its first
stage-2 packet about 4095 times in 4096. Both sides slip through together
about once in 16.7 million handshakes, and only then does the timeout decide.

The confirmation packet exists because key confirmation would otherwise be
lopsided. The responder confirms on the initiator's VERSION. The initiator
would confirm only on the responder's VERSION, which the node sends only after
its message processing has accepted the initiator's
(src/net_processing.cpp:3720-3724). Any ordinary close by the responder in
between would look to the initiator exactly like an HX1 failure and trigger a
classical retry: a self-connection, which is closed before the responder's
VERSION is sent (src/net_processing.cpp:3708-3713); an inbound eviction, whose
candidates include peers still in the handshake (src/net.cpp:1689-1736;
src/node/eviction.cpp:180-217); a restart. With the confirmation packet the
initiator is confirmed about one round trip after VP_I, before the
responder's message processing has seen anything.

### Stage-2 key schedule

```
salt2   = "xcoin_v2_hybrid_mlkem768" || MessageStart                  (28 bytes)
IKM2    = K || ecdh_secret || ct || ell_I || ek || ell_R                (2464 bytes)
PRK2    = HMAC-SHA256(key = salt2, message = IKM2)                       HKDF-Extract
key(L)  = HMAC-SHA256(key = PRK2,  message = L || 0x01)                  HKDF-Expand, 32 bytes

initiator_L2 = key("xcoin_hx1_initiator_L")   length cipher,  initiator -> responder
initiator_P2 = key("xcoin_hx1_initiator_P")   packet AEAD,    initiator -> responder
responder_L2 = key("xcoin_hx1_responder_L")   length cipher,  responder -> initiator
responder_P2 = key("xcoin_hx1_responder_P")   packet AEAD,    responder -> initiator
session_id2  = key("xcoin_hx1_session_id")
```

This is the same HKDF construction BIP324 uses
(src/crypto/hkdf_sha256_32.cpp:11-22), which accepts input key material of
any length (src/crypto/hkdf_sha256_32.h:19). MessageStart is the same 4 bytes
stage 1 appends to its salt (src/bip324.cpp:37-38). ek, ct, ell_I and ell_R
are the exact bytes that were sent. ecdh_secret is the stage-1 input
(src/bip324.cpp:41).

- No stage-2 label equals any BIP324 label (`initiator_L`, `initiator_P`,
  `responder_L`, `responder_P`, `garbage_terminators`, `session_id`;
  src/bip324.cpp:47-64). The four stage-2 keys MUST be derived only from
  PRK2, never from the stage-1 key material.
- Garbage terminators are not derived again: they belong to stage 1 and are
  already on the wire.
- The cipher objects start fresh. Each side discards its four stage-1 cipher
  objects and creates `FSChaCha20(initiator_L2, 224)`,
  `FSChaCha20Poly1305(initiator_P2, 224)` and the responder pair. It assigns
  them to send and receive by role exactly as src/bip324.cpp:44-54 does for
  stage 1. Every new object starts with packet counter 0 and rekey counter 0,
  so the first stage-2 packet in each direction uses nonce (0, 0) under a new
  key. The length cipher restarts its keystream the same way. Stage-2
  packets carry empty associated data.
- Both stages count from 0. They never reuse a key and nonce pair only
  because their keys differ, so tests MUST assert that the eight keys (four
  per stage) are pairwise different.

### What a node reports

`getpeerinfo` keeps `transport_protocol_type` and `session_id`
(src/rpc/net.cpp:195-196, 302-303) and adds one boolean field,
`transport_hybrid`. No new transport type is added
(src/node/connection_types.h:91-95).

| Connection state | `transport_protocol_type` | `session_id` | `transport_hybrid` |
|---|---|---|---|
| Before the peer's version packet (as today, src/net.cpp:1589-1597) | `detecting` | `""` | false |
| Classical v2, after the peer's version packet (any mode) | `v2` | stage-1 session id | false |
| HX1 negotiated, no stage-2 packet from the peer authenticated yet | `detecting` | `""` | false |
| HX1 after key confirmation | `v2` | session_id2 | true |
| Plaintext v1 | `v1` | `""` | false |

The stage-1 session id of a hybrid session is never reported. If it were, a
quantum attacker in the middle could relay ell_I and ell_R unchanged, rewrite
the version packets and leave both ends showing the same id. Anyone comparing
session ids out of band MUST compare `transport_hybrid` as well: a matching
classical id between two nodes that both run mode 1 is exactly what an
offer-stripping attacker produces.

The "New outbound peer connected" log line (src/net_processing.cpp:3885-3899)
names the hybrid state. `getnetworkinfo` adds `v2hybrid` (the mode: `off`,
`prefer` or `require`) and `v2hybrid_counts`, counters since startup:
- `hybrid`: key confirmation reached;
- `classical`: the peer's version packet classified **none** in prefer mode;
- `refused`: require mode turned a peer away;
- `bad_record`: a **malformed** record, or an ek that failed the check;
- `stage2_failed`: the peer's first stage-2 packet had a length over 4095 or
  did not authenticate, or the handshake timed out while the session was
  hybrid and not yet confirmed;
- `local_error`: this node's own ML-KEM or RNG call failed;
- `classical_retry`: classical retry connections actually opened.

Every failure in the next section logs at info level, rate-limited, because
today every v2 failure line is debug-only (src/net.cpp:1137, 1195, 1224, 1239,
2056). These fields are official-software policy, not wire protocol; other
implementations need not copy them.

### Failure handling

| Event | prefer (1) | require (2) |
|---|---|---|
| Peer's version packet classifies as **none** | continue classical | disconnect |
| Inbound connection is plaintext v1 | v1, as today | disconnect after 16 bytes |
| Outbound: nothing received and at least 24 bytes sent (today's v1 retry condition, src/net.cpp:1555-1570) | reconnect with v1, as today | disconnect, no reconnect |
| Record classifies as **malformed** | disconnect, count `bad_record`, retry once | disconnect, count `bad_record` |
| ek fails the FIPS 203 section 7.2 check | disconnect, count `bad_record`, retry once | disconnect, count `bad_record` |
| Local ML-KEM or RNG failure | disconnect, count `local_error`, no retry | disconnect, count `local_error` |
| After the switch and before key confirmation: the peer's first stage-2 packet has a length over 4095, or does not authenticate | disconnect at once, count `stage2_failed`, retry once | disconnect at once, count `stage2_failed` |
| After the switch and before key confirmation: the handshake timeout | disconnect, count `stage2_failed`, retry once | disconnect, count `stage2_failed` |
| After the switch and before key confirmation: the peer closes the connection | retry once | nothing more |
| Decryption failure after key confirmation | disconnect (BIP324) | disconnect (BIP324) |

"Retry once" applies to outbound connections only; see the next paragraphs.

**Never downgrade on a local error.** A failure of this node's own key
generation, encapsulation, decapsulation or random number source MUST
disconnect and MUST NOT continue with an empty version packet. Sending "none"
because our own ML-KEM call failed would quietly produce a classical session
nobody asked for. (The node's RNG aborts the process rather than fail,
src/pqrandom.cpp:26-28, but the ML-KEM library's error returns are still
checked.)

**One classical retry, prefer mode only.** When an outbound connection in mode
1 is lost after the initiator received a VP_R carrying the HX1 tag and version
(classified **HX1** or **malformed**) and before key confirmation, the node
reconnects once to the same address with the same connection type, as the v1
retry does (src/net.cpp:1946-1957).
- Causes that qualify: a malformed record, a failed ek check, a stage-2
  failure (a length over the limit, a packet that does not authenticate, or
  the handshake timeout), and the peer closing the connection.
- Causes that do not: a local error, and any disconnect this node decided on
  itself (`disconnectnode`, a ban, shutdown, the network being turned off).

The reconnection runs that one connection in mode 0: it ignores the offer,
sends an empty VP_I, and ends classical. A retried connection is never retried
again for HX1, though today's v1 retry still applies to it. Mode 2 never
retries. The reasons are under "Rationale".

Each retry is logged at info level with its cause (`bad_record`,
`stage2_failed`, or "closed before key confirmation"). It is counted in
`classical_retry` when the retry connection is actually opened, not when it is
queued. Between two correct HX1 nodes the only ordinary cause left is the peer
closing in the one round trip before it switched to stage 2, for example an
inbound eviction or a restart during the handshake; the responder's own log
names that close. Any other retry points at a real HX1 bug, which therefore
shows up as a rising count, not as silence.

**The retry must not be lost.** A queued reconnection is keyed by destination
and is dropped without a trace if a connection to that destination already
exists (src/net.cpp:3030-3031; PerformReconnections ignores the result,
src/net.cpp:4151-4175). For addnode and `-connect` peers (MANUAL connections)
that happens whenever a fresh attempt comes first: the addnode thread opens
its attempts before it drains the queue (src/net.cpp:2979-2998), and the
`-connect` loop drains it once per pass, after opening every address in the
list (src/net.cpp:2540-2557). The fleet's own addnode links depend on these
connections (contrib/regenesis/vps/bootstrap.sh:109). So the classical retry
sticks to the destination: the node marks the address "next attempt
classical" (in its AddedNodeParams entry, src/net.h:111-114, or in a
per-destination set that OpenNetworkConnection consults for MANUAL
connections), whichever loop opens the next connection to it uses mode 0, and
the mark is cleared when that connection is opened.

**Timeouts are unchanged.** The existing handshake timeout (`-peertimeout`,
default 60 s, src/net.h:93; enforced at src/net.cpp:2013-2061) covers the
whole HX1 exchange. No new timer is added. A timeout that ends a connection
while it is hybrid and not yet confirmed (src/net.cpp:2054-2059) counts as
`stage2_failed` and qualifies for the classical retry. With the first-packet
limit this is rare.

### Secrets

- In modes 1 and 2 only, ecdh_secret is kept from the stage-1 derivation
  until the stage-2 derivation, the classical decision or the object's
  destruction, then wiped. `Initialize` copies it into a buffer from
  secure_allocator (src/support/allocators/secure.h:20) and wipes its local
  ECDHSecret as today; ECDHSecret itself is a plain std::array
  (src/key.h:30). In mode 0 nothing is kept: `Initialize` wipes the secret
  exactly where it does today (src/bip324.cpp:66-70).
- The responder keeps dk, or only the 64-byte seed d ‖ z and derives dk again
  at decapsulation (FIPS 203 section 3.3 allows storing the seed), until
  decapsulation or the classical decision.
- m, K, IKM2, PRK2 and the stage-2 key bytes are wiped as soon as the four
  stage-2 ciphers exist. The stage-1 cipher state of both directions is wiped
  at the switch.
- Everything retained lives in locked, wiped-on-free memory and is wiped on
  every path: success, classical fallback, every error, and object
  destruction. BIP324Cipher has no destructor today (src/bip324.h:19-94); HX1
  needs one.
- ML-KEM keys are fresh for every connection and never cached. A cached ek
  would link a node's onion and clearnet identities; a cached dk would end
  forward secrecy.
- d, z and m come from the node's strong RNG. FIPS 203 section 3.3 asks for at
  least 192 bits of RNG strength for ML-KEM-768. Each is its own 32-byte
  GetStrongRandBytes call: that function serves at most 32 bytes per call and
  asserts on more (src/random.cpp:567, 607-609), so one 64-byte draw of
  d ‖ z would abort the node on every inbound v2 connection, which any peer
  could cause. If the ML-KEM library draws its own randomness instead, its
  random-bytes hook MUST split requests into 32-byte calls the way
  src/pqrandom.cpp:31-36 does. That shim serves only PQClean's
  `PQCLEAN_randombytes`; the ML-KEM library's hook is a different function
  and needs the same loop. Either way the same bytes go on the wire. Fixed
  seeds are for tests only.

### Kill switch

`-v2hybrid=0` is the escape hatch if HX1 misbehaves, so it MUST NOT share
HX1's code on the connection path. In mode 0 a transport:
- makes no ML-KEM call and takes no HX1 branch in the V2Transport state
  machine;
- wipes ecdh_secret inside `Initialize`, where it is wiped today
  (src/bip324.cpp:66-70), and allocates no HX1 state;
- for the same inputs, entropy and garbage, produces the same bytes, the same
  state changes and the same disconnect decisions as v31.99.0-pre1.

Mode 0 still runs a little shared code that cannot change the wire, and
nothing else: the BIP324Cipher destructor (it wipes memory that is already
wiped), the classical-retry check when a connection closes (always false in
mode 0), the counters, and the new RPC fields. So mode-0 `getpeerinfo` output
differs from v31.99.0-pre1 only by the added `transport_hybrid` field, always
false, and `getnetworkinfo` only by `v2hybrid` (`off`) and the counters.

The reference implementation guards every HX1 branch with the mode. CI gate:
the existing transport tests, unmodified, pass in mode 0:
`net_tests/v2transport_test`, the seven pinned `bip324_tests` packet vectors
(src/test/bip324_tests.cpp:202-306), and the `p2p_transport_*` fuzz targets.
Those tests only see output, so a mode-0 unit test also asserts that no ECDH
secret is kept after `Initialize` and that no HX1 state is allocated.

Mode 0 on one node makes that node's links classical and keeps them up against
every peer in mode 0 or 1. That is why the default is prefer (see
"Rationale").

## Rationale

**Why the version packet.** BIP324 reserves its contents for exactly this and
today's receivers ignore them (src/net.h:464-467; src/net.cpp:1249-1255;
the tree's own tests already send random contents up to 999 bytes,
src/test/net_tests.cpp:1427, 1450). So HX1 needs no service bit, no flag day
and no change to already-released binaries. ek and ct travel inside
encrypted packets, so the byte stream still looks random to a passive observer,
which BIP324 requires. Rejected:
- Changing the key messages in place. Old and new nodes would fail with each
  other and never fall back, because the v1 retry only fires when nothing was
  received (src/net.cpp:1555-1570). Raw ek bytes are also easy to spot: all
  768 coefficients are below 3329.
- A new service bit. More code at every connection call site, it still needs
  an in-band marker, and it gains nothing.
- A TLS or SSH style layout (ek after ell_I, ct after ell_R). It puts ek and ct
  in the clear, and an old responder would swallow ek as garbage and carry on
  classically while the new initiator misreads the stream.

**Why the responder generates and the initiator encapsulates.** The
responder's version packet leaves in the same flight as its key, because it
already has the initiator's key when it answers. That makes it the natural
first half of an exchange. The initiator's version packet is the reply. Today
the initiator sends it the moment it has the responder's key and becomes
ready at once (src/net.cpp:1150-1171, READY at 1157). With HX1 it waits for
VP_R, which arrives in that same flight, so the delay is only the time to
encapsulate. Inbound peers send VERSION only after receiving one
(src/net_processing.cpp:3720-3724), so the responder has nothing to send
between VP_R and VP_I anyway. The reverse order would let the inbound side do
only the cheap encapsulation, but the responder would have to hold VP_R until
VP_I arrived, which adds a full round trip to every connection.

**Why this combiner.** The ML-KEM secret comes first and the ECDH secret after
it. That order is modelled on the hybrid secret NIST SP 800-56C Rev. 2 allows,
Z′ = Z ‖ T: the secret from the standardized scheme first, an auxiliary shared
secret after it. HX1 then appends public transcript values (ct, ell_I, ek,
ell_R) to the same extraction input, much as X-Wing hashes its X25519
ciphertext and public key together with the two secrets. SP 800-56C puts only
shared secrets in Z′ and public context in its FixedInfo, so HX1 is modelled
on it but does not conform to it, and claims no SP 800-56C compliance. The
security argument is of the kind the TLS 1.3 hybrid design draft makes for its
concatenated secrets: HKDF-Extract (HMAC-SHA256 keyed with the fixed salt) is
treated as a random oracle, or at least as a dual PRF, so its output looks
random as long as either K or ecdh_secret is unknown to the attacker. That is an assumption
about HMAC-SHA256, not a proven property. Hashing ct and ek as well means the
result does not depend on ML-KEM's binding properties, which do not hold for
every key format. The ElligatorSwift keys are already
inside ecdh_secret; repeating them costs one more hash block. The salt is fixed
and public; the transcript goes in the input key material, not the salt,
because the transcript contains values the peer chose. The labels are new so
that a mix-up with stage-1 derivation cannot produce working ciphers by
accident. Such a mix-up (both directions on one key, or stage 2 equal to
stage 1) would still interoperate between two copies of the same buggy code.

**Why an 8-byte tag, a version byte, a kind and a length.** Upstream BIP324
may one day define its own version-packet contents, probably starting with
small numbers. An 8-byte xCoin tag cannot collide with that, and random
contents match it with probability 2^-64. The version byte lets a later HX
version be ignored cleanly by HX1 nodes. The length and the rule that trailing
bytes are ignored let a later version offer two records in one packet, as
long as the HX1 record comes first. The alternative, having HX1 nodes search
all records for version 01, was rejected: it would mean parsing records of
versions this node does not know, whose layout a later version is free to
change, where reading only the first keeps parsing to one fixed header.

**Why unknown means classical but malformed means disconnect.** Unknown
contents are BIP324's promise to future extensions, and prefer mode keeps it.
A record that carries our tag and version but the wrong kind or length can
only come from a broken or hostile HX1 implementation. Continuing quietly
would hide exactly the bug the rollout needs to see. In prefer mode the
initiator's classical retry still keeps the link. Contents that carry the tag
and version 01 and then stop inside the 12-byte header are malformed for the
same reason: unrelated contents match the tag and version with probability
2^-72. (An earlier draft called anything under 12 bytes "none", which made
two rows of the table overlap for 9 to 11 bytes.)

**The mainnet default at genesis is prefer (1), not require (2).** Every
mainnet node at genesis runs this release, because no mainnet-capable binary
exists before it: every published build refuses to start on mainnet
(src/kernel/chainparams.cpp:81, 740; src/init.cpp:943-947). So require would
cost no compatibility on day one. It is still the wrong default:

- Against the threat HX1 exists for, a passive recorder, prefer gives the same
  protection. The offer sits inside encrypted packets, and a passive observer
  cannot remove it. At genesis every link between default nodes is hybrid
  either way.
- What require adds is resistance to active attackers: refusing the forced v1
  reconnect and the stripped offer. BIP324 is unauthenticated, so the same
  attacker can simply sit in the middle and read everything. Require raises
  their cost a little and does not stop them.
- Require breaks the kill switch. If an HX1 bug appears after launch, an
  operator who sets `-v2hybrid=0` under a prefer network keeps every link,
  now classical. Under a require network the same node is cut off by every
  default peer. The only fix is then a coordinated flip or an emergency
  release during launch week.
- Require also refuses every plaintext v1 client: crawler-based DNS seeders,
  monitoring tools and any other implementation that has not adopted HX1.
  Their number at genesis is unknown.

Operators who want require can set it on their own nodes. Making it the default
needs its own XIP, and should wait until the measured share of classical
peers is near zero, an outside cryptographic review has happened, and a
fleet-wide rollback has been rehearsed.

**The classical retry is worth having.** At genesis every node is new. A bug
that only shows between two new nodes (one CPU architecture against another,
one network magic, the rekey boundary) would otherwise drop every such link on
every attempt, because there is no v1 retry once bytes have arrived
(src/net.cpp:1555-1570). At genesis that means a partition and possibly
competing chains. The retry turns that into a visible, counted fall back to
classical v2, which is still encrypted. Its security cost is nothing an
attacker does not already have:
- A passive attacker cannot trigger it.
- An attacker who can cut a connection after VP_I is on the path and active.
  That attacker can already force a plaintext v1 reconnect today, by
  withholding the responder's first bytes (src/net.cpp:1555-1570, 1946-1957),
  which is worse than classical v2. They can also simply sit in the middle.

Require mode, where neither retry exists, is the setting for anyone who wants
to refuse both downgrades.

**Why a first-packet limit, not a new timer.** Without the limit, every
stage-2 key mismatch is a silent 60-second stall (see "First stage-2 packet
and key confirmation"), so the classical retry, the `stage2_failed` counter
and require mode's disconnect all come a minute late. At genesis, where every
node is new, an HX1 bug would hold each outbound slot for 60 seconds per
attempt. A shorter timer would still stall, and a timer is one more thing to
get wrong. The limit costs nothing, because no correct first stage-2 packet
comes near 4095 bytes. Requiring the initiator to see exactly an empty decoy
would catch a mismatch slightly more often, but a wrong key already fails
about 4095 times in 4096 on each side, and one limit for both directions is
simpler. The handshake timeout still counts as `stage2_failed` and still
triggers the retry, for the rare case where both sides slip through together.

**Why a confirmation packet, and why a close still counts.** The other way to
stop ordinary closes from triggering the retry would be to leave "the peer
closed the connection" out of the retry rule. That would also drop the retry
when the responder's HX1 code wrongly rejects VP_I, which the initiator can
only see as a close, and that is exactly the new-to-new bug the retry exists
for. The confirmation packet keeps the close in the rule and shrinks the
window in which an ordinary close can look like a failure to one round trip.

**Review of 2026-09-25.** Two reviews attacked this XIP and its Python
reference: one on the cryptography, one on the protocol against the real
V2Transport. The cryptography review re-derived every vector from the text
with its own code and OpenSSL 3.6.4 for ML-KEM, and found no break in the key
schedule. The two reviews reported twelve findings, eleven of them distinct
(both found the 60-second stall). Each was checked against the code at
c07d047. All were accepted and none was rejected. They led to:
- the first-packet limit and the confirmation packet;
- a classical retry that leaves out local disconnects, logs its cause, is
  counted when the retry connection opens, and sticks to the destination;
- the ECDH secret kept only in modes 1 and 2, in locked memory;
- d, z and m drawn as separate 32-byte calls;
- the locking rule for the stage-2 switch;
- an exact definition of the kill switch;
- classification rows that do not overlap, and the HX1 record first;
- a corrected "Old" in the interop matrix;
- corrected wording for the combiner. The combiner itself is unchanged:
  changing it would change every vector to fix a sentence.

Where a review offered a choice, this XIP took one option and declined the
other:
- 9 to 11 bytes of tag and version 01 are malformed, not none.
- HX1 nodes read only the first record, rather than search for version 01.
- The retry is a mark on the destination, rather than draining the queue at
  the top of the addnode loop, which would not cover `-connect`.
- The limit is 4095 bytes, BIP324's garbage limit; one review suggested 4096.
  Either works.

**Why report "detecting" until key confirmation.** Today v2 is reported only
after the peer's version packet has been received and verified, "confirming
that the other side very likely has the same keys as us"
(src/net.cpp:1589-1590). For a hybrid session the equivalent proof is the
first stage-2 packet. Keeping `transport_protocol_type` at `v2` and adding a
separate boolean leaves existing consumers and tests alone: two new nodes
still report `v2` and equal session ids
(test/functional/p2p_v2_transport.py:58-62).
Nothing in the pool, explorer or miner reads these fields (a search of
xcoin-pool/, explorer/ and miner/ finds no reader).

**Why the size difference is accepted.** VP_R makes the responder's first
flight 1196 bytes longer. With BIP324's random garbage of 0 to 4095 bytes a
single connection often hides it, but several connections reveal whether a
node speaks HX1. That a machine runs an xCoin node is already visible from its
ports and peers, so no padding is added. Decoy packets could pad later without
a protocol change, since receivers already skip them.

## Backwards compatibility

HX1 is Policy. It changes no block or transaction rule, and a node that never
heard of it stays in consensus. Transport is per link: the worst any mismatch
can do is drop a connection.

### Interop matrix

"Old" is any classical BIP324 implementation that ignores version packet
contents, as BIP324 requires: v31.99.0-pre1, the fleet's current testnet A
build (same transport code), and third-party nodes. The test framework's
Python peer as released at v31.99.0-pre1 is **not** Old: it asserts that the
version packet is empty (test/functional/test_framework/v2_p2p.py:221 at
c07d047), so as an initiator it fails on the OFFER of any N1 or N2 responder.
The framework as changed alongside this XIP behaves as N0 in its default mode
0, and speaks HX1 in modes 1 and 2 (see "Tests that change"). N0, N1 and N2
are this release in modes 0, 1 and 2. "v1-only" is any node started with
`-v2transport=0`.

| Initiator \ Responder | Old | N0 | N1 | N2 | v1-only |
|---|---|---|---|---|---|
| **Old** | classical | classical | classical (old ignores the offer and answers empty) | dropped after VP_I; old keeps retrying v2 and never falls back to v1 | v1, as today |
| **N0** | classical | classical | classical | dropped after VP_I | v1, as today |
| **N1** | classical (empty VP_R) | classical | **hybrid** | **hybrid** | v1, as today |
| **N2** | dropped after VP_R, no retry | dropped after VP_R | **hybrid** | **hybrid** | fails: v2 is tried, no v1 retry |
| **v1-only** | v1 | v1 | v1 | refused after 16 bytes | v1 |

When an N1 to N1 handshake fails, the one classical retry turns that cell into
classical. N0 is byte-identical to Old in every cell. Old nodes need nothing:
they already ignore version packet contents.

### Mainnet

The question of old versus new binaries does not arise for mainnet: no binary
that can run mainnet has been published, and the genesis release is the first
one (src/kernel/chainparams.cpp:81). Every mainnet node at genesis starts in
the N1 row unless its operator chooses otherwise. Seed addresses still enter
addrman without NODE_P2P_V2 (src/protocol.h:354), so in prefer mode the first
automatic connection to a seed is plaintext v1 until the seed's own version
message updates addrman. That gap exists today and HX1 does not change it.

### Testnet A

Testnet A has old nodes: the practice release, the fleet's current build,
and at least one node run by an unknown third party. The default is prefer
there too, so every cell with an old node stays exactly as it is today and
upgraded nodes go hybrid among themselves. Setting require on a testnet A
node cuts it off from all of them.

### Tests that change

- `V2TransportTester::ReceiveVersion` expects an empty version packet
  (src/test/net_tests.cpp:1266-1273). Existing cases run in mode 0 unchanged;
  new cases cover modes 1 and 2.
- The random version-packet contents at src/test/net_tests.cpp:1427 stay
  valid: they classify as **none** and the session stays classical.
- The Python framework at c07d047 asserts an empty version packet
  (test/functional/test_framework/v2_p2p.py:221), so it cannot connect as an
  initiator to an N1 or N2 node. Any tree or CI job that still carries that
  framework, including branches whose v2 test files have diverged, breaks
  against an HX1 node until it takes the change. The changed framework keeps
  the contents in `received_version_contents` and ignores them in mode 0, its
  default, and speaks HX1 in modes 1 and 2. It also reads on after a decoy
  instead of stopping at it (test/functional/test_framework/p2p.py:336 at
  c07d047), because the confirmation packet is a decoy that can share a read
  with the messages after it.
- The pinned BIP324 vectors (src/test/bip324_tests.cpp:202-306) do not
  change: stage 1 is untouched.

## Deployment

A Policy XIP needs no activation. The steps below are the conditions for
shipping HX1 in the genesis release. Nothing here counts as decided until
this XIP is merged (XIP-1, "No decision counts as made until its XIP is
merged").

1. **Library.** ML-KEM-768 comes from a vendored, reviewed implementation
   that performs the section 7.2 key check, reports RNG failure and wipes its
   secrets. The recommendation is PQCA mlkem-native v2.0.0, portable C only,
   kept off the public include path because its header names collide with
   ML-DSA-65's (src/CMakeLists.txt:59-65), with its random-bytes hook routed
   to src/pqrandom.cpp:29-38. PQClean's ML-KEM is archived and skips the key
   check.
2. **Tests before any node runs it:** everything under "Test vectors and
   tests" below, plus a local regtest churn run of at least 10,000 handshakes
   across the interop matrix (old binary against new in modes 0, 1 and 2,
   both roles), asserting the transport type and the disconnect reason for
   each one.
3. **Measure first.** Record the `v2hybrid_counts` baseline and systemd
   restart counts on the current build before upgrading anything.
4. **Testnet A canary order, with rollback binaries kept on every machine:**
   one leaf relay node for 24 to 48 hours; then the other relay nodes; then the
   founder's desktop node; the node that also runs the pool and explorer last.
   At least one node stays on the old build for the whole soak.
5. **Soak.** 72 hours of mixed versions. Pass criteria are counts per
   interop-matrix cell, zero `stage2_failed` and `bad_record` between fleet
   nodes, every `classical_retry` logged with a cause and each "closed before
   key confirmation" retry matched to a close the responder logged, and no
   restarts. Rehearse the kill switch on one node:
   restart it with `-v2hybrid=0` and confirm every link comes back classical.
   Any transport fix restarts the 72 hours.
6. **Mainnet magic check.** Before the release, connect a pair of
   mainnet-parameter nodes over loopback in both roles, past 224 packets each
   way, and confirm `transport_hybrid` on both ends.
7. **Genesis release** (XIP-3) with the default `-v2hybrid=1`, then the same
   canary order on mainnet.

## Reference implementation

Being written on a branch of the public tree at v31.99.0-pre1; linked here
when published. The code touch points:

- `CConnman`: the classical-retry mark on the destination for MANUAL

- `Transport::Info` and `CNodeStats` gain the hybrid flag
  (src/net.h:231-234, 270-274); `getpeerinfo`, `getnetworkinfo`, `addnode` and

- `-v2hybrid` registered beside `-v2transport` (src/init.cpp:568) and checked

## Test vectors and tests

### ML-KEM-768 primitive

An implementation MUST pass all of these before it is used in HX1:

- NIST ACVP `ML-KEM-keyGen-FIPS203` and `ML-KEM-encapDecap-FIPS203`, every
  ML-KEM-768 case, including decapsulation of modified ciphertexts. Pin them
  as a JSON file the way src/test/data/ml_dsa_65_fips204.json pins ML-DSA-65.
- The accumulated vectors of Go's `crypto/mlkem` (`TestAccumulated`). A
  SHAKE128 stream over the empty string supplies, for each iteration,
  d ‖ z (64 bytes), m (32 bytes) and a random 1088-byte ciphertext. A second
  SHAKE128 absorbs ek, ct, K, and the decapsulation of the random ciphertext.
  The result is the first 32 bytes of the second stream. For ML-KEM-768:
  100 iterations `1114b1b6699ed191734fa339376afa7e285c9e6acf6ff0177d346696ce564415`,
  10,000 iterations `8a518cc63da366322a8e7a818c7a0d63483cb3528d34a4cf42f35d5ad73f22fc`.
  The generator behind this XIP reproduces both.
- The C2SP CCTV ML-KEM sets for bad encapsulation keys (every one MUST fail
  the section 7.2 check), unlucky NTT sampling, and `strcmp`. Do **not** use
  CCTV's "accumulated pq-crystals" hash (`f7db260e…`) as a FIPS 203 check:
  it does not match the final standard's key generation (see the note below).
- A cross-check against OpenSSL 3.6.4: key generation from a 64-byte seed
  (`-pkeyopt hexseed:`), encapsulation with a fixed m (`-pkeyopt hexikme:`),
  and decapsulation both ways must give identical bytes.
- The known answers in the last block of the handshake vectors below.

### Handshake vectors

Generated by a Python program that is separate from the C++ implementation
and from the test framework's HX1 state machine. It
uses the tree's own Python BIP324 code (ChaCha20, FSChaCha20,
FSChaCha20Poly1305, HKDF from test/functional/test_framework), checked first
against the pinned C++ vector at src/test/bip324_tests.cpp:202-216. The
ElligatorSwift keys and the ECDH secret come from the tree's libsecp256k1, the
same `secp256k1_ellswift_create` call `CKey::EllSwiftCreate` makes
(src/key.cpp:312-326), and match the framework's pure-Python ECDH. ML-KEM
comes from a pure-Python FIPS 203 implementation checked against OpenSSL 3.6.4
and Go's accumulated vectors. A C++ test can use the existing
`V2Transport(nodeid, initiating, key, ent32, garbage)` test constructor
(src/net.h:656) with aux as ent32, plus the ML-KEM seeds.

Two more programs reproduce every vector value below. One is the test
framework's HX1 state machine, through
contrib/testgen/gen_hx1_handshake_vectors.py, which writes
src/test/data/hx1_handshake_vectors.json. The other was written for the
review of this XIP from RFC 8439 and BIP324 alone, with its own ChaCha20,

stage-1 keys, both garbage terminators and the stage-1 session id (which
equal what unmodified BIP324 derives); SHA-256 of ek and dk; SHA-256 of ct and

confirmation packet; five full stage-2 application packets per direction

data. These are opaque test bytes, not P2P messages. In every hybrid vector

index 0), so its application packet i has stage-2 index i + 1.

### The quantum-adversary test

Interop tests cannot catch the worst bugs, because two copies of the same
wrong code agree with each other. This test checks the property HX1 exists
for.

1. Run a real handshake between two new transports, in both role
   assignments, with decoys injected in both stages, and exchange at least 230
   application packets in each direction, past the 224-packet rekey. Record
   both byte streams.
2. Give the test both ElligatorSwift private keys, as a quantum computer that
   breaks ECDH would have them. Derive the stage-1 keys, parse both streams,
   and decrypt VP_R and VP_I; that is allowed, they carry only ek and ct.
3. Assert that every packet after the version packets fails authentication
   under the stage-1 keys, both with the stage-1 counters continued and with
   them restarted at 0.
4. Assert that the first application message (the initiator's VERSION) comes
   after VP_I, and that nothing but decoys and VP_I was sent under stage-1
   keys.
5. With dk (or d ‖ z) added, derive the stage-2 keys **outside the
   implementation under test**: Python `hmac` and `hashlib`, plus an
   independent ML-KEM (Python, or OpenSSL 3.6.4). Assert that every packet
   after the version packets decrypts and matches what was sent.

Only after this passes can the `transport_hybrid` flag be trusted. The
generator behind the vectors above runs steps 2, 3 and 5 on its own streams.

### Other required tests

- Distinct keys: the eight stage-1 and stage-2 keys are pairwise different,
  and the same plaintext encrypts differently in the two directions.
- The V2TransportTester matrix: new against new and new against classical, in
  both roles, in modes 0, 1 and 2; unknown tag; unknown version; the bare
  tag; 9 to 11 bytes of tag and version 01 (malformed); wrong kind; wrong
  length; truncated body; trailing bytes; a later version's record in front
  of the HX1 record (none); each bad ek of V6 and every CCTV bad key; a random
  ct (each side fails at once on the first stage-2 packet from the other, not
  at the timeout); a packet sent by the responder between VP_R and VP_I
  (fails); decoys before and after the version packets; v1 refused in mode 2.
- The first-packet limit: a first stage-2 packet of exactly 4095 bytes of
  contents is accepted; one of 4096 fails as soon as its length is read; a
  node never sends a larger first stage-2 packet; after key confirmation
  larger packets pass.
- The confirmation packet: the responder sends exactly one 20-byte stage-2
  decoy right after its switch and before anything else; the initiator is
  confirmed before the responder's VERSION; a responder that closes after
  reading the initiator's VERSION (a self-connection) leaves the initiator
  confirmed and not retrying.
- Injected local failures at key generation, encapsulation and decapsulation:
  each disconnects, none produces a classical session, and the node that
  failed never retries. (After a responder's decapsulation failure the
  initiator only sees the connection close, and retries.)
- The classical retry: two new nodes with a deliberately mismatched stage-2
  derivation end up classical after exactly one retry, with the counter at 1
  and counted when the retry connection opens. For an addnode peer the retry
  survives a fresh attempt by the addnode thread, and for `-connect` a list
  of two or more addresses. A `disconnectnode` or ban before key confirmation
  does not retry. A handshake timeout of an unconfirmed hybrid session counts
  as `stage2_failed` and retries.
- The real random path: key generation and encapsulation fed by
  GetStrongRandBytes, with d, z and m as separate 32-byte calls, not only
  fixed seeds.
- Secret wiping on every exit path.
- Fuzz: extend `p2p_transport_bidirectional_v2`, `_v1v2` and
  `bip324_cipher_roundtrip`, and add ML-KEM encapsulation and decapsulation
  targets.
- Mode 0: the kill-switch gate above, and the unit test that no ECDH secret
  survives `Initialize` and no HX1 state is allocated.

### Note on the CCTV accumulated hash

The C2SP CCTV ML-KEM page lists
`f7db260e1137a742e05fe0db9525012812b004d29040a5b606aad3d134b548d3`
for 10,000 "accumulated pq-crystals" ML-KEM-768 tests. An implementation of
the final FIPS 203 does not produce it; the generator behind this XIP produces
`f959d18d3d1180121433bf0e05f11e7908cf9d03edc150b2b07cb90bef5bc1c1` for the
same procedure. With one change, key generation hashing d instead of d ‖ k
(the FIPS 203 draft; the final standard adds k in Algorithm 13, line 1), the
same generator reproduces `f7db260e…` exactly. That hash therefore tests the
draft, not the standard. Go's accumulated vectors above are the ones to pin.

## Security considerations

**What HX1 protects.** The contents of every packet after the version packets
on a link where both ends run HX1: transaction relay and its origin, address
gossip, inventory and requests. They are protected against someone who records
the traffic now and later breaks secp256k1, as long as ML-KEM-768 holds, and
against a classical attacker as long as either holds. Keys are fresh for
every connection, and FSChaCha20 already rekeys every 224 packets inside a
connection.

**What it does not protect.**
- **An active attacker in the middle, now or later.** The transport is still
  unauthenticated. A classical attacker who substitutes both ElligatorSwift
  keys reads everything, as with BIP324 today; the two ends then show
  different session ids. A future quantum attacker in real time could strip
  the offer and leave both ends classical with matching stage-1 session ids,
  which is why `transport_hybrid` must be compared along with the id.
- **Forced downgrades in prefer mode.** An attacker on the path can force a
  plaintext v1 reconnect (existing behaviour) or a classical retry. Require
  mode refuses both.
- **Plaintext v1 links**, including first contact with seed addresses, which
  enter addrman without NODE_P2P_V2 (src/protocol.h:354). Those are readable
  now, not just later. A separate change could tag seeds with NODE_P2P_V2;
  the existing v1 retry would cover seeds that only speak v1.
- **Metadata:** IP addresses, timing, packet and flight sizes, and whether a
  node speaks HX1.
- **The peer itself**, which sees everything it is sent.
- **Coins and consensus**, which HX1 does not touch. They rely on ML-DSA-65 and
  SLH-DSA signatures.
- VP_R and VP_I are protected only by stage-1 keys. A future quantum attacker
  learns ek and ct from them. That is harmless: both are public values in any
  KEM.

**Resource cost per handshake.** Measured on the founder's M3 Pro with
OpenSSL 3.6.4: ML-KEM-768 key generation 27.5 µs, encapsulation 18.2 µs,
decapsulation 28.4 µs. Today's inbound v2 handshake does about 85 µs of
elliptic-curve work.

| | Responder (inbound) | Initiator (outbound) |
|---|---|---|
| Extra CPU | key generation + decapsulation, about 56 µs at OpenSSL speed; estimated 55 to 150 µs with portable C | key check + encapsulation, about 20 µs at OpenSSL speed |
| Extra bytes sent | 1216 (VP_R grows from 20 to 1216; the confirmation packet adds 20) | 1100 (VP_I grows from 20 to 1120) |
| Extra memory while the handshake is open | under 6 KB (ek, dk or seed, ecdh_secret) | under 3 KB (ek, ct, K, ecdh_secret) |
| Extra hashing | HMAC over 2464 bytes, a few µs | same |

The inbound total rises from about 85 µs to an estimated 140 to 235 µs, all on
the single socket thread (src/net.cpp:1738, 2188). The portable-C figure
must be measured on the x86-64 relay nodes and the 1-CPU nodes before
release.

**Denial of service.** A peer triggers the responder's key generation by
sending 64 arbitrary bytes, which already triggers an ECDH today, so the
attacker's cost is unchanged and ours rises by one key generation.
Decapsulation needs a VP_I that authenticates under stage-1 keys, so the
attacker must do a real ECDH first; a random ct costs the same as a valid one.
The bandwidth an attacker can draw per TCP connection grows by about 1.2 KB.
Existing inbound connection limits and eviction bound all of this. A
per-address-group handshake rate limit can be added later without a protocol
change. A crash in the new parsing code would be reachable by anyone for the
price of one ECDH. That is why parsing is a fixed 12-byte header with exact
lengths, why it must be fuzzed, and why the rollout is staged with one node
left on the old build.

**Implementation hazards that interop tests do not catch:** sending VERSION
under stage-1 keys; stage 2 equal to stage 1; one key used for both
directions; reporting the stage-1 session id; downgrading on a local error;
skipping the section 7.2 check; reusing an ML-KEM key across connections;
timing differences on implicit rejection; waiting on a wrong-key length
instead of failing at once; keeping the ECDH secret in mode 0; drawing more
than 32 bytes from GetStrongRandBytes in one call; switching the send ciphers
without the send lock. Each one has a required test or review rule above.

**Upstream divergence.** src/bip324.* and src/net.cpp are unchanged from
Bitcoin Core today. HX1 makes them diverge for good, and every future upstream
transport merge has to be re-checked against this XIP.
